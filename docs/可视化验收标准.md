# 可视化验收标准

> 这份东西是从「脚本成片 · 参考片复刻」这条线的三轮验收里攒出来的。
> 它先是这条线的验收清单，**更是后面每一条线的模板**——其他模块按同样的
> 要求和目标去验证、优化、修改、验收。

---

## 一、目标是什么

不是「功能能跑通」。是：

> **一个人坐在屏幕前，看着 Agent 把活干完，全程知道它在干什么、走到哪了、
> 有没有卡死。**

判据只有一条：**这件事能不能让那次录像更顺、更好看。**

功能对不对是次要的——软件早就能跑通了，但人对着一块不动的板子等十四分钟，
这条线就不算做好。

## 二、四条硬指标

### 1. 每一步都有话说，而且是人话

- 说**它在做什么**，不是说它调了什么接口
- 三类分开：进度（走到哪了）/ 判断（为什么改主意）/ 发现问题（可能要喊停）
- **判断类最值钱**。「标签命中 5318 条太宽，改用画面描述再搜一轮」这种话，
  是人肯把花钱的活交给静默模式的唯一理由

### 2. 慢步骤必须有进度，而且带分母

超过十几秒的等待都算慢步骤。**分母按整件事算，不是按这一次调用算。**

> 反例：打标是按行调用的，只报「这一行第 2/3 镜」——人还是不知道整体
> 走到哪了。
> 正例：「正在看第 12 句的第 2 个参考镜（**全片 23/47 镜**）」

人要的不是「正在打标」四个字，是**看着一个数字一路涨到头**。
跨调用也得接得上：这次是从第 23 镜接着往下，不是从 0 重来。

### 3. 界面要跟着走，而且看得出在动哪儿

- 它做哪一行，界面就**滚到**哪一行——包括视口外的行（懒构建的列表要先粗滚
  再精调，不然一过第四行界面就死住）
- 正在做的那一行要**比人自己选中更醒目**（更粗的边 + 发光），
  不然人得盯着播报条读字才知道
- **不许每条命令都把页面推倒重建**。Agent 每跑一条命令都是新进程、都会
  唤醒一次，无条件 pop+push 等于视图不停弹回第一行

### 4. 「在忙」和「坏了」必须分得开

黑图 + 红按钮 = 人以为坏了。正在下载就说「正在下载这条素材…」，
真失败就说「没下下来，点一下重试」。

## 三、曾经的死结，以及它是怎么消失的

**死结**：可视模式要求界面停在这个任务上，而 Agent 写这个任务要求界面
**不能**停在上面（它占着写锁）。于是最该让人看见的那几步，恰恰因为
「人在看」而做不了。

**错解**：让界面退出那个任务去腾锁——一退出人就什么都看不见了。
（更糟的是这条路还依赖「恰好还有第二条任务」，只有一条任务时彻底死锁。）

**过渡解**：界面把写锁让出来但留在页面上，自己转成只读跟随。
那仍然是在绕这个死结，而不是解掉它。

**现在（2026-09-18 起）：整套锁删掉，死结跟着消失。** 人开着那一页，
Agent 照样写得进去；Agent 在干活，人也随时能自己上手改。界面跟着 Agent
走（它改哪一行就滚到哪一行），但**不是只读**。

敢这么做的前提有两条，缺一不可：
- **唯一写入口**（`TaskMutation`）落盘前重读 + 校验版本，被抢写就重跑一轮，
  两边同时写不再互相抹掉
- **改动日志分得清人和 Agent**，谁改了什么查得到——看到人动过手就停下来问他

这条对应产品负责人的原话：「永远不要让 Agent 报一个问题说『我现在没有办法
操作，因为软件那边没有给我权限』……任何它不应该做的事情，都应该是人告诉
Agent 的，而非是软件限制的。」

## 四、反复出现的几类洞（照着查，不用重新发现）

### A. 说的和做的不一样

- **报成功、实际没存**：`applied` 从「提交内容」算，跟落盘结果没关系。
  → **落盘后回读，报你存进去的东西**
- **三态混成两态**：「没问题」和「没查成」都是空值，长得一模一样。
  → 「有问题 / 都干净 / 没看成」三条分开说
- **一句话套两种错**：「这个 id 不在候选里」和「你压根没给候选清单」
  是两回事，混着说会让人去查错的东西

### B. 人能看到的，Agent 拿不到

人在界面上看得见画面、一眼看出「这条烧着字」；Agent 拿到的只有一个数字。
→ 凡是人眼能判断的事实，`--json` 里都要有对应字段

### C. 同一件事两处算

界面读对了、命令行三处各写各的都漏了回落 →
**取法收敛成一处**，两边都走它。这个项目在这上面栽过不止三次。

### D. 手册和实际对不上

- 命令名不存在（`script from-video` 真名是 `extract`）
- 字段名写错（`description` 实际叫 `sceneDescription`）→ 照着写 jq 拿到
  一列 null，第一反应是「功能坏了」而不是「手册错了」
- 规则没写例外（「一屏别少于 4 字」没说整行就两三个字时不受限）
- **给的命令自己犯了自己警告的错**（用 `jq '.x // "干净"'` 把 null 折叠掉）

→ 这些都要有测试守着，而且**测试要从代码里抓真名**，不能手写白名单
（手写的名单漏过 `script` 整整一条线）

### E. 影响成片的检查被静默跳过

素材没下到本地 → 画面自查整批跳过 → 全是「未检查」→ 一路混到成片。
→ **当场点名，并给出能照做的补救命令**；别只在日志里写一行 warn

## 五、怎么验收

**用一个完全干净的 Agent**，不给它任何上下文，起手就是
`ishkafel skill --install`，然后一句话交待需求。

给它三条硬规矩：

1. **撞到走不通的地方立刻停下来报告，不许自己发明绕法。**
   它一绕，问题就藏起来了
2. 不许做破坏性操作（删任务、删文件、重装）
3. 不许自己用 ffmpeg / 手写关键词绕开工具

**要它报告「第一反应是什么」**——报错把人往哪个方向引，比报错本身更值钱。
真机上一句措辞不准的报错，让验收 Agent 去重装 CLI、删任务、重建任务，
整轮白干。

跑完之后**看它的报告，也看人在屏幕前看到了什么**——这两件事经常不一样：
上一轮它成功交付了成片，而人在旁边看到的是十四分钟黑屏。
