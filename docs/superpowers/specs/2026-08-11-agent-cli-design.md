# 2026-08-11 让 Agent 驱动全流程：CLI 设计

> 目标：Agent（Claude Code / Codex / 任何能跑 bash 的）能独立完成
> 「导入 → 分析 → 挑素材 → 配乐 → 导出」，人只看成片；也可以在任意一步
> 停下来，把 GUI 弹出来转人工。

---

## 一、贯穿全篇的一条原则

> **软件提供事实与保护，skill 提供方法论。**

这条线划掉了一大批看起来该做、其实不该做的功能：

| 事情 | 归谁 |
|---|---|
| 「挑素材要看前后是否顺畅」 | **skill**。软件只负责把上下文这个*事实*开放出来 |
| 「同一批微调版素材要挑差异大的」 | **skill**。软件只负责如实给出候选与它们的元数据 |
| 「跑飞了会烧掉多少磁盘」 | **调用方**。软件如实说明代价，但不设闸门——我是工具，你来调用我 |
| 「Agent 和人同时写同一份数据」 | **软件**。这是数据安全，不能指望调用方自觉 |
| 「ASR 的时间戳准不准」 | **软件**。见第三节，这一步不许外包 |

判据是：**这件事出了问题，谁承担后果、谁有能力判断**。挑得好不好由 Agent
承担且只有它能判断；数据被覆盖了是软件的锅，因为只有软件看得见两个写入方。

---

## 二、为什么是 CLI，不是 MCP Server

**不必须用 MCP，第一版也不做。**

- `lib/core/` 本来就是纯逻辑（`AnalysisPipeline` / `ExportRunner` /
  `TrackPlanBuilder` 都不依赖 UI），加第二个入口 `bin/` 的成本很低
- 任务是**文件存储**（`FileTaskRepository` → JSON 落盘），Agent 和 GUI 天然
  读同一份数据，**不需要任何进程间通信**
- **跨 agent 平台**：Codex 用不了 MCP，但谁都能跑 bash。这是决定性的一条
- 人也能直接跑同一条命令来复现问题；MCP 要专门的客户端才能调试
- 项目里已经有 miaoa CLI 这个先例，用户和 agent 都不用学新东西

将来真需要 MCP（比如给不会用 bash 的 agent 用），在 CLI 之上包一层很薄的
翻译即可。**不预先做**。

---

## 三、哪些 AI 步骤可以外包给 Agent

### 划线的依据：输出可不可验证

一开始设计的是「能力协商」——让调用方声明自己有什么能力。**这个设计是错的**，
因为它隐含一个不成立的前提：*Agent 的能力和内置 API 等价*。

真正的问题不是「它会不会声明错」，而是：**有些步骤即使它真有能力，我们也
无法判断它做得对不对**。

所以改成按**输出可验证性**划线，由软件规定固定清单，不由调用方声明：

| 步骤 | 输出 | 可验证？ | 结论 |
|---|---|---|---|
| 语义切分 | 哪几句归一组 | ✅ 索引连续、不重叠、覆盖全部、边界落在句子边界 | **可外包** |
| 打标 | 从受控词表里选几个 | ✅ 必须在词表内 | **可外包** |
| 切点矫正 | 给定候选切点留不留 | ✅ 只能对给定候选表态 | **可外包** |
| 挑素材 / 组方案 | 选哪几个候选 id | ✅ 必须在候选列表里 | **可外包** |
| **ASR 转写** | 文本 + **时间戳** | ❌ 没法验证 | **不可外包** |
| TTS / 声音克隆（将来） | 音频 | ❌ 没法验证 | **不可外包** |

**ASR 为什么是硬边界**：时间戳偏 200ms 就足以毁掉整条链——切分错位、镜头
对不上、口型飘，而且**这个错不会报错**，一路静默到看成片才发现。文本本身
像模像样，人眼根本挑不出来。守住它换来的是「同一条视频，谁来跑、跑几次，
切分结果都一样」，这个确定性对一个交付成片的工具比省那几分钱重要得多。

顺带：外包出去的恰好是账单大头（切分与打标是按单元/镜头逐个调 LLM 的，
一条 51 个镜头的片子要调几十次），ASR 是一次性按时长计费的，反而便宜。

### 外包的机制

不是「声明能力」，而是**指定哪几步由外部做**：

```bash
ishkafel analyze <task> --external=segment,tag,shot-review
```

被指定的步骤不去调云端，而是把**输入**吐出来、把流程停在那里：

```json
{
  "status": "pending",
  "todo": [
    {
      "kind": "segment",
      "why": "把台词切成语义单元",
      "input": { "sentences": [{"index":0,"startMs":0,"endMs":1200,"text":"..."}] },
      "apply": "ishkafel apply segment <task> --file <你的结果.json>"
    },
    {
      "kind": "shot-review",
      "why": "这几处画面差异在灰区，要看图定夺切不切",
      "input": { "candidates": [{"atMs":12345,"frames":["/tmp/a.jpg","/tmp/b.jpg"]}] },
      "apply": "ishkafel apply shots <task> --file <你的结果.json>"
    }
  ]
}
```

Agent 用自己的能力处理，`apply` 回填，流程继续。**CLI 完全不需要知道调用方
是谁**——它只知道「这几步归你，那几步归我」。

### 回填必须过校验

**外包出去的是「判断」，不是「数据结构的定义权」。** 每一种回填都有硬校验，
不合格就拒绝并说明原因，让它重做：

| 回填 | 校验 |
|---|---|
| segment | 句子索引连续无缺口、不重叠、覆盖全部句子；每个单元至少一句；单元边界必须等于某个句子的边界 |
| tag | 每个标签必须在该层的受控词表内；数量不超过上限 |
| shots | 只能对 `input.candidates` 里给出的切点表态（保留/丢弃），**不能新增切点** |
| plan | 引用的候选 id 必须来自该镜头位的候选列表；每个单元/镜头至多一个取值 |

## 四、方案提交：放弃笛卡尔积

### 为什么

产品要求是**产出的每一条都能用**，而不是「导 60 条挑 3 条」。但这与笛卡尔积
冲突：

```
U1 挑了 3 个、U2 挑了 4 个 → Agent 挑 U2 时，「前面」是 U1 的哪一个？
```

笛卡尔积隐含「每个位置的每个候选都独立可用、任意搭配都成立」，而这恰恰是
「挑的时候要看前后是否顺畅」所否定的前提。

### 所以

**Agent 直接提交完整方案列表，CLI 逐条导出，不做组合展开。**

```bash
ishkafel apply plans <task> --file plans.json
```

```json
{
  "plans": [
    {
      "name": "A-厨房线",
      "units": [
        {"unit": 0, "mode": "whole", "material": 114799},
        {"unit": 1, "mode": "perShot", "shots": {"5": 116719}},
        {"unit": 2, "mode": "keepOriginal"}
      ],
      "bgm": [{"fromUnit": 0, "toUnit": 2, "material": 108, "volume": 0.25}]
    }
  ]
}
```

每一条都是 Agent 整体设计过的，所以每一条都能用。CLI 只管收方案、逐条导。

**GUI 保持现状**（人挑候选 + 笛卡尔积），两条路各走各的，互不影响。

## 五、命令清单

```
ishkafel import <video> [--project <id>] [--json]
    导入并建任务，返回 task id

ishkafel analyze <task> [--external=<steps>] [--json]
    跑分析。--external 指定哪几步交给调用方（见第三节）
    返回 status=done 或 status=pending + todo[]

ishkafel apply segment|tags|shots|plans <task> --file <json>
    回填外部结果。过不了校验就非零退出并说明哪一条不合格

ishkafel task <task> [--json]
    任务全貌：单元、镜头、标签、已选素材、方案、导出历史

ishkafel candidates <task> --unit <i> [--shot <j>] [--json]
    候选素材。带 miaoa 的图片 URL、标签命中数、时长差、名称、上传时间，
    以及**上下文**：本单元台词、相邻镜头已选什么及其画面描述

ishkafel bgm search <关键词> [--json]
    配乐候选

ishkafel export <task> [--out <dir>] [--json]
    按已提交的方案逐条导出。先输出「将导 N 条、约占 X GB、预计 Y 分钟」，
    不设闸门（那是调用方的判断），但如实说明

ishkafel open <task>
    把 GUI 弹出来并落到这个任务的工作台——转人工审核用
```

所有命令 `--json` 输出结构化结果；非零退出码表示失败，`stderr` 给可直接展示
的中文原因。

## 六、任务锁

Agent 在跑而人打开了 GUI，两边都写同一个任务 JSON——**后写的把先写的覆盖掉，
而且悄无声息**。这是真实的数据丢失，且只有软件看得见两个写入方，所以必须
软件来管。

- Agent 开始操作 → 在任务上打一把锁（写进任务目录，含持有者、起始时间、心跳）
- GUI 打开一个被锁的任务 → **切成只读**，顶部一条「Agent 正在操作这个任务」
- 人要抢 → 给「强制接管」按钮。接管后 Agent 的后续写入被拒绝并明确告知
- **锁必须能自愈**：心跳超时（建议 60 秒）自动释放。否则 Agent 一崩，
  这个任务就再也打不开了

## 七、留痕

每一步是谁做的要记进任务：内置 API 还是外部 Agent、哪个模型/版本、什么时候。
出了问题能查，而且用户看得见。现有的 `trace` 字段（打标过程）扩展一下即可。

这同时是**可复现性**的基础：Agent 有随机性，同样的指令两次跑结果可能不同，
排查问题时不可复现是灾难。

---

## 八、这一版不做

- **MCP Server**：等真有不会用 bash 的调用方再说（第二节）
- **组合差异度评估**：「这 60 条里实际只有 3 种形态」这类判断，等真跑出几十条
  才知道该怎么衡量。方案 A 之下它也不那么急——每条都是设计过的
- **产出排序 / 推荐**：产品要求是每条都能用，不是挑几条
- **导出前的强制闸门**：调用方的判断，我们只如实说明代价
- **本地 ASR（whisper 之类）**：能彻底摆脱云端 key，但那是另一件事

---

## 九、后续要做的（不在本 spec 范围内，但必须有）

**给 Agent 的 skill 文档。** CLI 只提供事实，「怎么挑得好」要靠它：

- 挑每一个镜头时都要看**前后是否顺畅**——本单元台词讲什么、相邻镜头是什么
  画面，避免「每个都对、连起来不对」
- 同一批素材常有**微调版**（1~5 号几乎一样、6~10 又一批），组方案时要挑
  差异明显的，否则几十条片子看起来是同一条
- 方案与方案之间要有可见差异，否则矩阵导出失去意义
- 校验失败了怎么读错误、怎么改

这份文档的地位等同于 miaoa 的 SKILL.md：**没有它，CLI 只是一堆能调用的动作，
产不出能用的片子。**

## 十、实现上的硬骨头

`AnalysisPipeline.analyze()` 现在是**一条龙跑完**的（抽音频 → 分离 → ASR →
切分 → 场景检测 → 打标 → 建单元）。要支持外部注入，它得改成**可分步、可中断、
可续跑**：每一步产出物落盘，从任意一步能继续。

这是本模块最大的一块工作，但它本身也是个改进——现在分析中途失败要整条重跑。
