# Agent 全权与操作日志：软件永远不对 Agent 说「不行」

**日期**：2026-09-17
**状态**：设计已定，待实施

---

## 一句话

**把软件里所有「Agent 拿不到权限」的代码全部删掉，换成一条说得清「谁在什么时候
改了什么」的日志。** 协作不靠软件裁决，靠 Agent 读日志自己判断。

---

## 从哪儿来的

产品负责人的原话（2026-09-17 的讨论，按顺序摘）：

> 我们要做的事情是，永远不要让 Agent 报一个问题，说是「我现在没有办法操作，
> 因为软件那边没有给我权限」。永远不要让它有这个报错，它永远有所有的权限。

> 只要这个 Agent 开始工作，它就跟人一样……核心就是，Agent 的操作要优先于人，
> 它的权限要高于人。

> 我们做这个软件，首先要让人好用，人觉得好用以后，人才能在这个软件上去给 Agent
> 打样，才能经过几次操作以后，引导 Agent 像人一样去操作，才能去写这个 skill。
> 然后当 Agent 操作习惯了以后，它就可以用静默模式直接调这个软件去执行了。
> **其实最终这个东西是要给 Agent 使用的，只不过在走到那一步之前，人一定得用得
> 舒服。** 在这个视角而言，Agent 是优于人的。

> 不管这个软件被人搞成了什么样子，当 Agent 开始工作的时候，它都可以去它任何想
> 去的地方，改它任何想改的内容，做它任何想做的事情。**任何它不应该做的事情，
> 都应该是人告诉 Agent 的，而非是软件限制的。**

关于人的改动该不该被 Agent 覆盖：

> 这个东西是 Agent 和人的沟通的问题，这个跟软件是没有关系的。软件只提供人能够
> 修改，然后 Agent 也能修改。软件只是在调用 CLI 的说明上告诉这个 Agent：如果你
> 发现这个是人已经修改的，且必要、且你还是要对它进行修改的时候，到底是绕过还是
> 要去修改，由 Agent 自己判断，或者由 Agent 引导 Agent 和人进行沟通。

关于日志：

> 软件要提供给 Agent 一个方式……类似于日志一样，就让 Agent 一目了然，知道它停
> 下来过后发生了什么，时间线是什么样子的。然后 Agent 就可以在每一次断开、重启
> 工作的时候去阅读这个东西。凭 Agent 的聪明才智，它一定能接上它原来的工作。

> 比如说 Agent 挑了四五个分镜，然后人删除了其中两个，**Agent 自己就应该能够通过
> 这个操作去总结出来：人不想要的分镜是哪个类型，即便人没说。**

> 你可以随便去抢，你可以趁 Agent 思考的过程里面赶紧把 3 给改了也行。但是我们有
> 日志，当 Agent 发现有问题的时候，它可以查这个日志，它就会知道「你小子在我思考
> 的时候把 3 改了」。

## 设计过程中被否掉的方案（记下来，免得重来）

讨论中间提过一个「驾驶权」方案：用一份盘上的 `driver.json` 表示「此刻谁在开车」，
人和 Agent 显式交接，界面上给一个「我来接手」按钮。

**被产品负责人否掉了**，理由是它多余：

> 如果我们做成这两点（全权 + 日志），是不是我们就可以不用去做这个东西了？就是
> 允许两个人抢操作了。当人发现抢操作的时候，应该是人去让 Agent 停止。这样也符合
> 我所设计的理念嘛，就是 Agent 是高于人的。

他是对的。驾驶权是在替人做防护，而防护一旦存在，就一定会在某个边角变成
「Agent 拿不到驾驶权」——那正是这次要清零的东西。**撞上了不用软件裁决，日志会
说清楚谁干的，人自己去 Agent 那头说停。**

所以本设计里**没有**任何形式的互斥、让位、接管、驾驶权。

## 这些场景，一个都不许卡

产品负责人点名列举的，逐条都是验收项：

- 退出某一个任务
- 进入任务列表页面
- 进入某一个任务
- 新建任务
- 从任务 3 切到任务 5
- **人把界面调到了任务 10，Agent 接手后又要接着干任务 3**
- Agent 干到一半人打断、手动改了东西，再让 Agent 接着干
- 人正开着某个任务看着，Agent 要写这条任务

> 「不管这个软件被人搞成了什么样子，当 Agent 开始工作的时候，它都可以去它任何想
> 去的地方，改它任何想改的内容，做它任何想做的事情。」

---

## 「Agent 高于人」具体落在哪两处

这句话不是口号，它在设计里只有两个着力点，除此之外两边是平等的：

1. **人不能在软件上停止 Agent。** 界面上没有「停止」「我来接手」这类按钮。人要停它，
   去 Agent 那头说——「应该是人去让 Agent 停止」。
2. **Agent 可以把人的界面带走，而且这条命令永不失败。** `ishkafel ui open <任务>`
   零等待、没有失败分支。人没有对称的能力去「把 Agent 拽回来」。

其余地方（谁能改数据、谁后写生效）两边**完全平等**，因为「谁该让谁」是 Agent 和人
的沟通问题，不该由软件裁决。

## 现状诊断：软件现在有 18 处对 Agent 说「不行」

### A. `exitLocked` —— 13 处

```
lib/cli/cli_output.dart:11   const int exitLocked = 4;  // 「被锁住了：别人正在操作这个任务」

script_run_command.dart:130,307,472,618   apply_command.dart:99
bgm_command.dart:101   export_command.dart:150   review_command.dart:231
unit_command.dart:84   voice_file_command.dart:86   jianying_command.dart:57
script_apply_command.dart:112   blank_command.dart:67   voice_command.dart:73,192
```

源头是 `TaskLockFile.acquire()` 返回的那个 `false`：

```dart
bool acquire(String holder, {DateTime? now}) {
  ...
  if (current != null && current.holder != holder && !current.isStale(...)) {
    return false;          // ← 所有卡点从这里长出来
  }
}
```

### B. 「界面没有回应」—— 5 处 `exitEnv`

`ui_command.dart:121,226,239`、`apply_command.dart:555`、`review_command.dart` 一处。

这一类比锁更隐蔽，因为它把**可视化变成了执行路径的一部分**：

> Agent 写不进去 → 委派给界面写 → 等界面 **90 秒** → 界面不在这一页 → 超时 →
> 报「界面没有回应」

于是可视化一出问题，就把 Agent 挡住了。因果是反的。

### C. 「颗粒度不对齐」查下来不在命令粗细上

产品负责人最初的说法是「Agent 调 CLI 的颗粒度，和人操作界面变动的颗粒度，一定要
对齐，现在并不是对齐的，很多操作跳来跳去」。

照着查了一遍 CLI 的命令面，**结论是命令粒度已经和人的操作基本一一对应**：

```
ishkafel unit subtitle <task> --unit 1 --shot 2 --text "…"   ← 人改一句字幕
ishkafel candidates <task> --unit 1 --shot 5                  ← 人点开一镜的候选
ishkafel bgm <task> --from 0 --volume 0.3                     ← 人调一段配乐音量
ishkafel unit audio <task> --unit 2 --shot 3 --audio vocals    ← 人给一镜单独选音轨
```

**所以不对齐的不是「一条命令等于几次点击」，是「界面跟不跟得住」**——Agent 一条接
一条地跑命令，而每条命令都是一个新进程，跨命令的连续性一处都没有。下面 D、E 两条
就是那个连续性缺口的具体形态。

### D. 跨进程防抖完全失效

`lib/cli/agent_stage.dart`：

```dart
DateTime _lastWakeAt = DateTime.fromMillisecondsSinceEpoch(0);
String? _lastWakeModule;
static const Duration _settleTime = Duration(seconds: 3);
```

注释里说得很清楚：唤醒会把页面**关掉重开**，所以叫过之后要给 3 秒落位，这期间
不再叫。**但 `AgentStage` 是每条 CLI 命令 new 一个的，而每条命令是一个新进程**
——这两个字段永远是初值，防抖等于没有。

于是：界面正在从工作台跳到审片台的那几百毫秒里，`ui_where.json` 还写着旧模块
（只有栈顶页面才报到，跳转途中没人写）→ 下一条命令的新进程读到「不在现场」→
`hasPendingUiWake` 又是 false（唤醒刚被取走）→ **再发一次唤醒 → 刚建好的页面被
销毁重建 → 画面弹回第一行**。

那个挨过骂的毛病没治好，只是从「命令内」挪到了「命令之间」，而 Agent 恰恰是一条
接一条地跑命令。

### E. 另外两处教 Agent 走废路

- `ui_command.dart` 里 `'next': 'ishkafel ui tasks && ishkafel script extract …'`
  和那条 `note`：让 Agent 建完任务先把界面支开，下一条命令再叫回来——**一次纯浪费
  的往返**。`lock.yield` 上线之后这条路就不必要了，提示没跟着改。
- `agent_stage_overlay._tick` 取「心跳最新的那条槽」：全局槽和任务槽同时有心跳时，
  焦点在两者之间抖。

## 设计

### 一、Agent 全权

**`exitLocked` 这个退出码整个作废。** 软件允许对 Agent 说「不行」的理由只剩三类：

| 退出码 | 理由 | 为什么允许 |
|---|---|---|
| `exitBadUsage` / `exitNotFound` | 参数、任务 id、单元下标不对 | 这是事实，不是权限 |
| `exitEnv` | AI 凭据没配、miaoa 不通、ffmpeg 不在 | 外部依赖真的坏了，Agent 自己修不了 |
| `exitFailed` | 干了但没成：ASR 没识别出、TTS 念岔、ffmpeg 挂了 | 活儿真没成 |

**没有第四类。**「有人占着」「界面在别处」「界面没回应」一条都不许留。

要删的东西：

- `lib/core/storage/task_lock.dart` —— 整个文件删掉（GUI 侧一并去掉，见下）
- `lib/cli/lock_yield.dart` —— 删掉
- `lib/cli/gui_lock_guidance.dart` —— 删掉
- `lib/cli/agent_lock_holder.dart` —— 删掉
- `UiAction.lockYield`（请界面让出写锁）—— 删掉
- `lib/features/workbench/task_lock_banner.dart` —— 删掉
- `exitLocked` 常量 —— 删掉
- `ui_command.dart` 里 `next` / `note` 中那条 `ui tasks` 往返 —— 删掉

界面上**不做**「我来接手」「停止 Agent」这类按钮。人要停它，去 Agent 那头说。

`ui tasks` 保留，但从「Agent 唯一的解锁出路」退回成一条普通的导航命令。

**界面那三处 `lock.acquire` 怎么办**（`director_page.dart:1325`、
`workbench_page.dart:234`、`review_page.dart:256`）：**什么都不换，直接去掉。**
界面打开一个任务不再需要「取得」什么，它就是打开。两边都能写、写盘前重读、每一笔
记日志——这三条成立之后，锁没有存在的理由。

后面第四节那个 `[跟过去]` 按钮不属于这一类：**它移动的是视线，不是控制权。**
点不点它，Agent 都在干同样的事。

### 二、委派降级：首选路径 + 秒级兜底

「界面在场时写操作委派给界面」这条原则**保留**——它保证人看到的和落盘的同源，
这个项目在「同一件事两处算」上栽过不止三次，不能退。

改的是它的地位：**从「必经之路」降级成「首选路径 + 秒级兜底」**。

1. **先读一眼 `ui_where`**：界面确实停在这条任务上，才走委派；否则**直接自己写，
   零等待**
2. 走委派的，超时从 **90 秒砍到 2 秒**
3. 超时后 **CLI 自己把活干了**，然后把结果告诉界面，界面在就跟上

第 1 条不能省。少了它，界面没开的时候每条写命令都要白等 2 秒——47 镜挑下来就是
一分半的纯等待，按 CLAUDE.md「每一次等待都要有交代」这就是不合格。**委派只在人
确实看着的时候才有意义，人不在就没有委派的理由。**

于是 `ui new-task` 界面没开也建得成，`apply plans` 界面停在任务列表也提交得了。
**可视化坏掉的最坏后果是「这一步没看见」，而不是「Agent 卡住了」。**

`UiAction.exportOpen` 是例外：它本来就是有意为之的「打开、填好，最后一下人点」
（花钱花时间，人在旁边时让他确认是对的），这条**交互**不改。但它同样受第 1 条管
——界面不在场时不走它，`ishkafel export` 自己导，不等任何人。

### 三、改动日志

#### 记什么

**只记写操作。** 只读一律不记——人的不记，Agent 的也不记（那属于「现状」，见第四节）。

每一笔改动一条，**带足判断依据**。这一条是整个日志的价值所在，判据就是产品负责人
举的那个例子：

> Agent 挑了四五个分镜，人删了其中两个。Agent 要能自己看出来「人不想要的是哪个
> 类型」。

```
❌  14:22  人  删除 U3S1、U3S4

✅  14:22  人  删除 U3S1
             ├ 素材 105475 · 抖音带货 · 标签[实拍,产品特写,手持]
             ├ 时长 2.4s（这一句要 3.1s，选它会 0.77x 变速）
             └ 画面描述：手持喷瓶对着灶台喷洒，画面右下有平台水印
    14:22  人  删除 U3S4
             ├ 素材 114798 · 标签[实拍,产品特写,倒放]
             └ 画面描述：特写倒出液体，右上角烧着「XX旗舰店」
```

第一种写法，Agent 读完只知道「人删了两个」。第二种写法，它一眼看出**两条都是产品
特写、两条都带别人的字**——人一个字没说，意图已经在那儿了。

这跟 `docs/可视化验收标准.md` 里那条「凡是人眼能判断的事实，`--json` 里都要有对应
字段」是同一条规矩，只是这次落在日志上。

#### 记录形状

```json
{"seq": 481,
 "at": "2026-09-17T14:22:07.412+08:00",
 "by": "human",                          // human | agent
 "actor": "人（工作台）",                  // 界面/进程标识，出问题时要说得出是谁
 "task": "t_3",
 "op": "shot.remove",
 "where": {"unit": 3, "shot": 1},
 "before": { ...足够判断的事实... },
 "after": null,
 "note": "人在时间线上右键删除"}
```

- `seq` 单调递增，是 `--since` 的游标
- `by` 只有两个值，**这是产品负责人点名要的**：「这个日志是要区分人的操作和 Agent
  操作的」
- `before` / `after` 里放的是**事实**不是 id：素材 id、标签、画面描述、时长、烧字、
  品牌、变速比——凡是人眼在界面上能看见的，这里都要有

#### 落在哪、留多久

`<dataDir>/logs/<taskId>.jsonl`，一行一条。**跟着任务走，任务删了日志一起删**
——不留孤儿数据（CLAUDE.md 最高准则里那条）。

#### 怎么读

```bash
ishkafel log <任务>                  # 人看的版式，倒序
ishkafel log <任务> --json           # 一行一条 JSON
ishkafel log <任务> --since <游标>    # 我上次看到这儿，后面发生了什么
ishkafel log <任务> --by human       # 只看人干了什么
```

#### 谁负责写

**唯一一处写入点**，界面和 CLI 都走它，不许各写各的。这个项目在「同一件事两处算」
上栽过三次，日志是第四次的完美候选——漏记一处，Agent 查到的「什么都没发生」看起来
正好像「一切正常」（见记忆 `feedback-report-what-you-store`）。

加一条架构测试：所有会改任务数据的写入路径都必须经过日志写入点。

#### 日志之外还要一处：当前数据上的来源标记

产品负责人的原话是「**如果你发现这个是人已经修改的**」——「发现」这个词要求它
**看当前数据时就能看见**，而不是必须先去翻一遍时间线。

所以除了日志，`task --json` / `candidates --json` 里每一处可改的东西都带一层来源：

```json
{"unit":3,"shot":1,"materialId":105475,
 "by":"human","at":"2026-09-17T14:22:07+08:00"}
```

两者分工，别混：

| | 回答 | 形态 |
|---|---|---|
| **日志** | 这中间**发生过什么**（包括已经被覆盖掉的中间状态） | 追加的时间线，要翻 |
| **来源标记** | 我**现在看到的这一处**，是谁定的、什么时候定的 | 当前值上的一个标记，一眼看到 |

Agent 给 U3 挑素材时看的是 `task --json`，那里直接写着「U3S1 是人在 14:22 定的」，
它当场就知道自己要动的是谁的东西——不用先意识到「我该去查日志」。

**同样只标事实，不给规则**：软件不说「人改过的不许动」，只说「这是人改的」。
绕开还是照改，是 Agent 的判断。

### 四、现状快照：`where` + `arrivedBy`

日志回答「**我不在的时候发生了什么**」，是一条追加的时间线。
界面在哪一页、人在看哪一行，回答「**现在是什么样**」，是一份随时被覆盖的快照。

只读导航属于后者——人翻了二十个任务又翻回来，记进日志就是二十条噪音，而 Agent 真正
关心的只有一句：**他现在在哪儿**。

现有的 `ui_where.json`（界面每 2 秒自己写一次）做厚，并且明着给 Agent：

```bash
ishkafel where --json
```
```json
{"module":"workbench","task":"t_5","taskSeq":5,"taskName":"滴露浴室篇",
 "unit":2,"shot":1,"panel":"candidates",
 "arrivedBy":"human",
 "since":"2026-09-17T14:31:02"}
```

#### `arrivedBy` 是这一节的关键

它把两种长得一样的情况分开：

**A. 人根本没动**（界面停在任务列表、刚冷启动、或还在这条任务上只是滚到了别处）
→ Agent 照常把界面带到现场。这是现在的行为，对的。

**B. 人自己翻走了**（他按了返回、点开了任务 5）
→ 这是他**有意**要看别的。软件默认**不把他拽回来**，改成在界面上挂一条常驻横条：

```
Agent 正在「#3 滴露厨房篇」挑第 12/47 镜 · 它说：这批标签太宽，改用画面描述再搜一轮   [跟过去]
```

Agent 一步都没被挡，数据照常写，播报照常出；人点一下「跟过去」就回到现场。
**同一页面里滚到 U8 去看**，同一个处理：横条变成 `Agent 在 U4 · [跟过去]`。

#### 这不是在限制 Agent

`ishkafel ui open <任务>` **永不失败、零等待**。Agent 读到 `arrivedBy: human` 这个
事实，**它自己决定**：

- 「这几步很关键，他必须看见」→ 直接 `ui open` 把人带回来，软件照办，不打折
- 「他在看别的，不打扰，我先把这 47 镜挑完」→ 什么都不做

软件给事实 + 给能力，要不要打断人是 Agent 的判断。

而现在的代码是反的——`AgentStage._ensureOnStage` **每一步无条件把界面拽回来**，等于
软件替 Agent 定死了「一定要打断人」。

**要改的只是 B 那一半，不是整个拿掉。** 说清楚免得实现时改过头：

| `arrivedBy` | `_ensureOnStage` 怎么做 |
|---|---|
| 不是 `human`（界面自己落位、被 Agent 带过来的、刚冷启动） | **照旧自动带过去**——这是可视模式该有的样子，不动 |
| `human`（人自己翻走的） | **不自动带了**，改挂横条；要不要带回来交给 Agent 用 `ui open` 决定 |

`arrivedBy` 一旦变回非 `human`（Agent 用 `ui open` 把人带回来了，或者人自己点了
「跟过去」），自动跟随就恢复。**人翻走这件事只关这一次，不是一个要人手动解除的开关。**

### 五、返回信封：让 Agent 「一开口就知道」

CLI 是一条命令一个进程，Agent 思考的那 30 秒里软件**没有任何通道能戳到它**。所以：

> 做不到「它思考时就知道」，但必须做到「**它下次一开口就立刻知道**」。

**每一条命令的 JSON 返回里都带同一个信封**——包括只读命令：

```json
{"ok": true,
 "...": "本命令自己的结果",

 "ui": {"module":"workbench","task":"t_5","taskSeq":5,"taskName":"滴露浴室篇",
        "arrivedBy":"human",
        "onMyTask": false,
        "note":"人自己翻到 #5 去了。你这一步写的是 #3，他没看见"},

 "log":{"cursor":481,"othersSince":3,
        "hint":"你上一条命令之后别人改了 3 处：ishkafel log t_3 --since 478"}}
```

三个要点：

1. **`onMyTask` 是软件算好的布尔**，不让 Agent 自己比 id。软件知道这条命令操作的是
   哪条任务，也知道界面在哪条任务，直接给结论，再附一句人话说清后果。
2. **每条命令都带，只读的也带。** Agent 不需要「记得去查」，它思考完之后不管下一步
   干什么，那一条的返回里就写着人已经走了。它看的是它本来就要看的东西。
3. **长命令跑到一半人走了也要说。** `script voice` 跑五分钟，中途人翻走：
   - 命令当场在 stderr 上说一声「人刚翻到 #5 去了，后面这几句他看不见」
   - 最终信封里记 `ui.leftDuringRun: true`，让 Agent 事后知道**哪一段是没人看着跑过去的**

   这一条在验收标准里有分量：「人跟着看两遍才敢交给静默执行」，那就得让 Agent 知道
   哪几步其实没被看到。

**`othersSince` 的游标存在哪**：每条命令返回信封时，把当时的 log `seq` 落到
`<dataDir>/cursor/<taskId>.json`；下一条命令读它，数一数这中间有几条不是自己写的。
不要求 Agent 传参——它不用记得住任何东西。同时有两个 Agent 在跑时这个数会偏多，
**方向是保守的（可能多报，不会漏报）**，够用。

信封**一处实现、所有命令共用**，不许各命令各写各的。

**逐行输出的命令怎么带**（`candidates` 一行一条候选、`log --json` 一行一条记录）：
信封只挂在**最后一行的汇总对象**上，不往每一条数据行里塞。调用方按行读，最后一行
就是它的现状简报。

### 六、写盘前重读、只改自己动过的字段

这一条**不是权限，是记账准确性的前提**。

现在任务是整份对象落库（`repository.save(task)`），没有字段级合并。Agent 拿五分钟前
的快照整份写回，把人改的抹掉了——**而它自己不知道它抹了，所以日志里也不会有这一条**。
日志就成了假账，而假账比没账更糟。

（这个形状已经在 `feedback-two-writers-one-task-object` 里记过四例，这是第五个入口。）

所以：**所有写入路径在落盘前重读一次，只合并自己动过的那几个字段。**

### 七、软件与 Agent 的责任分界

**软件只做四件事：**

1. 人能改、Agent 能改，**谁都不被拦**
2. 落库不互相抹掉（第六节）
3. **如实报事实**，三样：
   - 这中间发生过什么（**日志**）
   - 我现在看到的这一处是谁定的（**当前数据上的来源标记**）
   - 人现在在看哪儿、是自己翻过去的还是被带过去的（**`where` + 信封**）
4. 提供播报通道

**剩下的软件一个字不管**：绕开还是照改、要不要先跟人说、怎么说、什么时候打断人
——全是 Agent 的判断。

手册（`docs/AGENT_SKILL.md`）那头加一段说明：这些字段是什么、什么时候你会撞见、
撞见了你手上有哪些出路。**给事实和出路，不给规则**——跟 `candidates` 那条一样
（「看不看图、怎么去重、选哪几个，全是调用方的判断」）。

### 八、顺带治掉「跳来跳去」

三个根因（见诊断 D、E），共同解是**把进程内的防抖状态落到盘上**：

- `_lastWakeAt` / `_lastWakeModule` 落盘，新进程读得到，`_settleTime` 才真的生效
- 界面**跳转途中**写一个「我正在去 review 的路上」的中间态，别让 `ui_where` 停在
  旧值骗下一条命令
- **换场（换模块）和移视线（滚到第 N 行）分成两种动作**：换场要慢、要少、能合并；
  移视线可以密
- 播报槽按当前任务定，不再比心跳时间戳（去掉跨槽抖动）
- 删掉 `ui new-task` 的 `next` 里那条 `ui tasks` 往返

---

## 不做什么（YAGNI）

- **不做驾驶权 / 互斥 / 让位 / 接管**——见「被否掉的方案」
- **不做推送通知**。CLI 一条命令一个进程，接不住；靠「写进手册让 Agent 勤查」又要它
  记得住。信封方案让它不用记也不会漏。
- **不做只读操作日志**——那属于「现状」，`where` 已经回答了，记进日志只是噪音
- **不做冲突检测与自动合并策略**。谁后写谁生效，日志里看得出来，剩下的是 Agent 和人
  的沟通问题
- **不做日志的字段级回滚 / undo**。这次只解决「知道发生了什么」，撤销是另一件事

## 分期（这份设计装不进一个实施计划，得拆）

顺序是有讲究的：**日志必须先于删锁**。锁一删，两边就真的能同时写了；这时候要是
日志还没上、或者还在拿旧快照整份写回，第一件事就是静默丢改动——那比现在的卡点糟。

| 期 | 做什么 | 做完能验什么 |
|---|---|---|
| 一 | 写盘前重读、只改自己动过的字段（第六节） | 两边同时改不再互相抹掉 |
| 二 | 日志：唯一写入点 + `ishkafel log` + 数据上的来源标记（第三节） | 人删两个分镜，Agent 读日志说得出删的是什么；`task --json` 里看得出哪几处是人定的 |
| 三 | **删锁**：13 处 `exitLocked` + 界面三处 + 委派降级（第一、二节） | 全程不出现任何一句「没有权限」 |
| 四 | `where` + `arrivedBy` + 返回信封（第四、五节） | 人翻走之后 Agent 下一条命令就知道 |
| 五 | 跳来跳去（第八节） | 盯屏幕，画面不弹回第一行 |

## 架构测试要守住的

1. **没有任何 CLI 命令返回 `exitLocked`**（常量删掉，编译期就挡住）
2. **没有任何 CLI 命令因为「有人占着」「界面没回应」返回失败**——扫失败分支的措辞
3. **所有会改任务数据的写入路径都经过日志写入点**（不许绕过去自己 `save`）
4. **所有 CLI 命令的 JSON 返回都带信封**（`ui` + `log` 两个键）
5. 现有那条「不许裸调 `writeAgentPresence`」的测试保留

## 怎么验收

沿用 `docs/可视化验收标准.md` 第五节的办法：**一个完全干净的 Agent，不给任何上下文**，
起手 `ishkafel skill --install`，一句话交待需求。三条硬规矩不变（撞到走不通立刻停下
报告、不许破坏性操作、不许自己用 ffmpeg 绕开工具）。

这次额外要验的四件事：

1. **全程不许出现任何一句「没有权限 / 被占着 / 界面没回应」**。出现一次就是不合格
2. **中途人为制造干扰**：Agent 干到一半，人把界面翻到别的任务、手动删掉两个分镜、
   再翻回来。Agent 接着干**不能有任何卡点**，而且它读完日志要能说出「人删了哪两个、
   为什么我认为他不想要那一类」
3. **人翻走了它得知道**：Agent 跑一条命令拿到「界面在任务 3」，人当场把界面翻到
   任务 5，Agent 下一条命令的返回里**必须**写着他走了、这一步他没看见
4. **跳来跳去**：全程盯屏幕，画面不许弹回第一行，不许在模块之间来回抖

动过预览链路的话，`./scripts/preview_health.sh <任务ID>` 照跑。
