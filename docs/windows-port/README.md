## 三条先说在前面的硬约束

**一、成片必须逐像素一致。**
界面可以有细微差别（见 06），但**导出的 mp4 不行**。同一条任务、同一套方案，
在 macOS 和 Windows 上导出，画面应当逐帧一致、字幕逐像素一致。出口是要交给
客户的片子，两台机器出来不一样就是事故。

**二、字幕渲染必须换实现。**
现在成片字幕是 `osascript -l JavaScript` 调 macOS AppKit 画的
（`lib/core/subtitle/subtitle_rasterizer.dart`），Windows 上一行都用不了。
这是整个移植里唯一「不换实现就无解」的地方，也是上面那条约束的关键。
建议见 06 第三节。

**三、不静默降级。**
这是这个产品最核心的工程规矩（`CLAUDE.md` 有整节）：影响最终成片的东西出了错
就直接失败并点名，不许悄悄少一段、少一句、或用默认值顶上。移植时最容易违反它——
比如「Windows 上找不到 ffmpeg 就跳过这一段」。**不要这么做。**

## 已知的外部未知数（本包答不了，需要去问）

| 未知数 | 为什么要紧 | 现状 |
|---|---|---|
| **miaoa CLI 有没有 Windows 版** | 它是素材检索的唯一通道，没有它「替换裂变」整条线断掉 | 现在靠 `curl -fsSL https://miaoa.mininglamp.com/api/cli/install.sh \| bash` 装。退路：架构文档写着「miaoa REST API（**或**内置 miaoa CLI 子进程）」，当初就留了直连 API 这条路 |
| **audio-separator 在 Windows 的可用性** | 人声分离（换音色时要把原声里的人声剥掉） | uv 有 Windows 版，理论可装；onnx 后端与 GPU 加速是另一套。**Windows 上 CUDA 版是有意义的**（macOS 上没有），可能反而更快 |
| **剪映 Windows 版的草稿格式** | 草稿 JSON 里写死了 `"os": "mac"` 和 macOS 的字体绝对路径 | 需要在 Windows 上实测：草稿根目录在哪、`os` 字段要写什么、路径用 `\` 还是 `/`、有没有 URL scheme 能直接打开草稿（macOS 版实测没有） |

## 这一包不包含什么

- **不含任何代码改动**。仓库里 `lib/` / `macos/` / `windows/` 一个字节没动。
- **不含实现计划**。怎么分期、先做哪块、要不要抽平台抽象层，由接手方定。
  06 里有我的建议，但那是建议。
- **不含 Windows 侧的验证**。本包所有结论都来自 macOS 上的代码与真机；
  凡是写「Windows 上会……」的地方，都是推断，**接手方应当自己验一遍**。
