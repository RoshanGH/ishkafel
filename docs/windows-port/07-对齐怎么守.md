# 七、对齐怎么守

> 「长期双平台并行 + 功能对齐 + 像素级对齐」不是靠人记住的，要有机制。
> 这一份讲机制。

---

## 7.1 三层机制

| 层 | 守什么 | 怎么守 |
|---|---|---|
| **契约测试** | 功能对齐 | 同一组用例跑两个平台实现，少实现一个方法就是红的 |
| **视觉基准** | 像素对齐 | 两边同页面截图，与 `ui-baseline/` 对照 |
| **差异清单** | 允许存在的不同 | 唯一一份文档，**不在清单上的差异 = bug** |

---

## 7.2 契约测试（守功能对齐）

### 做法

如果采纳了 `06-移植建议.md` 6.4 的平台抽象层，每个接口配一组**契约测试**：

```
test/core/platform/
├── platform_paths_contract.dart      ← 一组用例，参数是「一个 PlatformPaths 实现」
├── platform_paths_macos_test.dart    ← 用 macOS 实现跑那组用例
├── platform_paths_windows_test.dart  ← 用 Windows 实现跑同一组用例
├── platform_shell_contract.dart
└── ...
```

Windows 实现可以在 macOS 上用**假文件系统 + 假环境变量**跑
（这个项目已经大量使用这种注入模式，比如 `MediaToolsLocator` 的
`ExecutableProbe` / `PathLookup`、`ProcessRunner`、`JsonPoster`）。

### 价值

- 加一个方法，两边都得实现，否则红
- 改一条规则，两边行为都得跟着变，否则红
- **不需要两台机器**就能发现大部分不对齐

### 现成的样板

这个项目已经有一条完全同构的机制可以照抄：
**`test/architecture/agent_parity_test.dart`** ——
「人在界面上能拧的每个旋钮，Agent 都要能拧」，它扫源码比对两套入口。

## 7.3 视觉基准（守像素对齐）

### `ui-baseline/` 是什么

28 张 macOS 真机截图，1440×900 窗口，Release 0.1.226。
每张的说明见 `ui-baseline/README.md`。

**它们是基准，不是参考。** Windows 侧做完对应页面后，
在同样 1440×900 窗口下截同一个页面，两张图应当：

- **布局完全重合**：栏宽、行高、间距、组件位置
- **配色完全一致**：所有色值来自 `04-UI视觉规范.md` 的同一份 token
- **文案完全一致**（除了 `02` 附二列出的那几项）
- **差异只落在文字抗锯齿层面**

### 工具

macOS 侧有两个脚本，**Windows 侧需要等价物**：

| 脚本 | 干什么 | Windows 等价物 |
|---|---|---|
| `scripts/shot_app.sh` | 给 app 窗口截图（不跟终端抢前台） | PowerShell + `Add-Type` 调 user32.dll（`FindWindow` + `PrintWindow`），或 `nircmd` |
| `scripts/click_app.sh` | 按**窗口内坐标**点击（截图上量到的 (x,y) 直接用） | 同上 + `SendInput` |

> `CLAUDE.md` 明确要求：**「UI 改动要真机跑起来截图核对，不允许只报『测试通过』。」**
> 这两个脚本不是可有可无的开发工具，是验收流程的一部分。

### 布局数值有测试钉着

比截图更硬的是 `04-UI视觉规范.md` 第 4.4 节列的那些测试——
它们断言的是**具体数值**（`totalHeight == 330`、`left == 560`、
`AppRadius.all == [4,6,8,12,999]`…）。

**这些测试两边都要跑，且必须是同一份。**
⚠️ 注意其中三条（`spacing_grid_test` / `radius_scale_test` /
`token_usage_guard_test`）写死了 Unix 路径分隔符，在 Windows 上会误报，
**要先改成跨平台写法**。

## 7.4 差异清单（守「允许的不同」）

### 唯一一份

建议在仓库里立一份 `docs/平台差异清单.md`，内容就是
`02-功能对齐清单.md` **附二**那张表，但**持续维护**。

规矩一句话：

> **不在清单上的差异 = bug。**

### 为什么必须是唯一一份

这个项目在「同一件事有两处说了算」上栽过不止三次
（`docs/2026-09-14-底片-design.md` 里那条最典型：画面来源在三处各答一遍，
结果画面和声音对同一个单元给出不同答案，一边有声一边黑屏）。

平台差异也一样：散在各个文件的注释里，等于没有。

### 加一条差异的流程

1. 先问：**这是「Windows 用户对操作系统的预期」，还是「ishkafel 的样子」？**
   （判据见 `06-移植建议.md` 6.2）
2. 是前者 → 写进清单，说明理由
3. 是后者 → **不许有差异**，去改实现

## 7.5 CI

两边都要跑：

```
flutter analyze
flutter test
```

`test/integration/` 默认 skip，需要真凭据 + 真网络 + 真 ffmpeg 才跑：
```
flutter test test/integration --tags integration --run-skipped
```

> 现在 macOS 上是 **4,366 项测试全绿**（含 52 条架构守卫）。
> **这是移植期唯一的安全网**，第一件事就该让它在 Windows 上也全绿。

---

## 7.6 交接给「那边的 Claude」时额外要做的

如果接手的是另一台机器上的 Claude Code，它**看不到这边的上下文，只能看代码
和这一包文档**。所以：

1. **`docs/windows-port/README.md` 是它的入口**，里面写了建议的阅读顺序
2. **仓库根目录的 `CLAUDE.md` 是最高准则**，本包不覆盖它。
   那里面有整节的工程规矩（「按商业化 To C 软件的标准做」「不静默降级」…）
3. **`docs/AGENT_SKILL.md` 是这个软件自己的操作手册**——
   Claude 可以用 `ishkafel skill --install` 把它装成技能，
   之后在任意会话里都能正确调用这个软件
4. 建议在 `CLAUDE.md` 里加一段 Windows 的说明
   （现在第 108 行只写了 macOS 的前台化问题）

## 7.7 一条最实在的提醒

`CLAUDE.md` 里这句话，对移植同样成立：

> **「能跑通」离「能用」还有很远。**
> 流程全绿、测试全过、片子导得出来，但人一听就知道情绪不对、
> 一看就知道镜头切碎了——这类问题不会出现在任何错误日志里。

移植期的对应版本是：

> Windows 版编译过了、测试全绿、片子也导出来了，
> 但字幕位置偏了两像素、时间线比 macOS 矮了一档、
> 中文在 11px 下糊成一团——**这些同样不会出现在任何日志里。**

所以最后一道验收只能是：**两台机器摆在一起，同一条任务，走一遍，逐屏看。**
