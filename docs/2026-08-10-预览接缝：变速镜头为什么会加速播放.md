# 2026-08-10 预览接缝：变速镜头为什么会加速播放

> 一个症状，四个独立的根因，其中三个我一开始都判错了。记下来是因为
> **判错的过程比结论有用**——它说明这类问题不能靠看代码想，必须量。
>
> 所有数字都在同一条真实素材上实测（滴露植源喷雾，96.2 秒，
> U2 的 S6 换成一条 5.503 秒的候选，坑位 2.867 秒）。

---

## 一、症状是怎么被描述出来的

用户前后描述了四次，每一次都更接近真相：

1. 「加速放慢速度的时候，整个播放是不流畅的，连音轨也会跟着变快或者变慢，
   播放指针也会突然加速突然变慢」
2. 「你其实是把从 S6 到最后所有的画面都加速了，然后保证它跟这个台词语义
   单元的结束时间对齐了」
3. 「单独播放 S6 没有问题，完整播放就出问题，影响到后面好多地方」
4. 「**必现的是播放到 S6 之后，它后面的几个 S 会被影响**；后面几个 U 偶发」

第 4 条是解题的钥匙——「影响范围紧跟在替换段之后、持续两三秒然后恢复」，
这个形状排除了"倍率算错"（那会全程一致），指向"某个一次性事件后的追赶"。

### 一个必须先澄清的误解

用户一度以为我们在播放器上做了变速：「你不要在轨道上或者在播放器上去进行
加速，你不是扯淡吗？」

**没有。变速是离线做完的。** 候选 5.503 秒，坑位 2.867 秒，ffmpeg 按
1.9195 倍加速渲染成一个独立文件（86 帧 / 2.866667 秒 / HEVC Main 10 /
30fps，与原片逐项一致），播放器拿到的就是四段顺序播：

```
edl://
  114799.mp4,        start=0,      length=16.300   ← U1 整体替换
  原片,               start=15.300, length=9.300    ← U2 的 S1~S5
  fit_0e42264b….mp4, start=0,      length=2.867    ← S6，已经加速好的成品
  原片,               start=27.467, length=68.766   ← S7 一直到片尾
```

全程没有一处设过播放速率。**"加速"是播放器自己丢帧追赶的结果，不是我们让它快的。**

这条 EDL 日志（`画面轨换源，共 N 段：…`）是排查中途加上的，也是最先派上用场
的东西——它直接证明了画面轨没有被连带加速：S6 之后是
`start=27.467, length=68.766`，原样播到片尾（27.467 + 68.766 = 96.233 = 原片全长）。

---

## 二、四个根因

按发现顺序。前三个都是真 bug，但都**不是**用户看到的那个"加速"。

### 根因 1：变速切片段没有认领它占的那段原片

**怎么发现的**：把真实数据灌进 `TrackPlanBuilder` 把轨道计划打出来看。

```
at=25600 dur=2867 in=0 srcStart=0 srcSpan=2867 /FIT_S6.mp4
                            ↑ 应该是 24600
```

**为什么**：建段时没写原片坐标，`sourceStartMs` 默认取了 `inMs`——而切片是
从头播的，`inMs` 就是 0。于是这一段一边声称自己对应「原片的 0~2.9 秒」，
一边把它真正占着的原片区间 24.6~27.5 秒**从映射表里挖成了一个空洞**。

**后果**：换轨时要按逻辑位置回到原处（记的是"我停在原片的哪一刻"，因为整体
替换会改变总长）。正播在 S6 里就是原片 25 秒左右，落进那个空洞，
`toComposedMs` 谁都不命中，兜底一句 `return totalMs` 把人一脚踢到片尾。
测出来的实际值就是 **53733，正好是片尾**。

触发点是"画面轨换了"的那一刻：切片刚渲染好、点一下 ★ 换候选、取消 ★。

**修法**：切片段带上 `sourceStartMs`/`sourceSpanMs` = 这个镜头的坑位；
`_merged` 合并时显式带原片坐标，不再靠 `inMs` 兜底；`toComposedMs` 落不进
任何一段时取最近段的边界，**不再一律甩到片尾**——真出了空洞，停在附近也比
看上去像播放器发疯强。

### 根因 2：纠偏 seek 每次都在制造下一次

**怎么发现的**：在纠偏日志里加上"seek 后的实际位置"。

```
口播轨偏了 -441ms，纠回来：目标 26333，seek 后 25892，主时钟 26333
口播轨偏了 -407ms，纠回来：目标 27166 …
口播轨偏了 -404ms，纠回来：目标 28000 …
```

间隔 833ms、幅度稳定 -400ms，25 秒里一条没有、一进 S6 就开始。

**为什么**：`seek` 不是瞬间完成的（实测 300~400ms），而目标取的是**发起那一刻**
的主时钟。等 seek 落地，主时钟已经走远了同样多——每纠一次就精确地制造出
下一次。声音每半秒被拽一下，听感就是"在快进"。

这解释了用户的第 2 次描述：「从 S6 到单元结束全都加速了，但结束时间卡对」——
被反复往前拽，到段末又被拽齐。

**修法**：按上一次的实测耗时前瞻（`_seekCostMs`，取均值、封顶 1 秒）；
上一次还没落地时不叠第二次；暂停时不前瞻（主时钟不走，多跳一段就是错位）。

### 根因 3：切片编码规格与原片不一致

变速切片一直是硬编码 `libx264 / yuv420p` 出来的，而原片是
`HEVC Main 10 / p010le`。预览把「原片 → 切片 → 原片」拼成一条 EDL，
**一个单元里就要重建两次解码器**，画面停约 100ms 再赶上去。

这条因果上一轮修下载素材时（`MaterialNormalizer`）已经验过一遍，只是当时
只覆盖了整体替换那条路，逐镜头变速这条漏了。

**修法**：`fitCandidateVideo` 收一个目标规格，编码器 / profile / 像素格式 /
分辨率 / 帧率全部对齐；帧数按目标帧率算（否则切片会比坑位长出或短掉几帧）；
规格进缓存键，旧切片自动作废重渲。

**顺带发现**：整体替换播的一直是 `material_cache/` 里的**原始下载**而不是
`material_normalized/` 里规格化过的那份——`_onMediaCacheChanged` 只
`setState` 没有重推轨道，规格化白做了。

### 根因 4（真凶）：画面轨只是拧了音量，没有关掉音频轨

前三个都修完，症状仍在。这时才装上**走时探针**：每一拍走掉的*内容*时长，
对得上真实过去的挂钟时间吗。

```
415ms 里走掉了 666ms 内容（1.60×），此刻 26099   ← 25.6s 正是 S6 切片起点
418ms 里走掉了 701ms 内容（1.68×），此刻 26800
400ms 里走掉了 666ms 内容（1.67×），此刻 31566
403ms 里走掉了 534ms 内容（1.33×），此刻 32100   ← 一路冲到 32.1s 才恢复
```

**从 25.6 秒开始，以 1.67 倍速连播了 6.5 秒内容。S6 只有 2.87 秒，
所以 S7、S8 整个被带着跑完。** 与用户第 4 次描述完全吻合。

**为什么**：变速切片是 `-an` 出来的（声音归口播轨管），**没有音频流**；
而它前后两段原片都有音频。画面轨此前只是 `setVolume(0)`——

> **音量 0 只是不出声，mpv 照样解码音频、照样拿它当同步基准。**

一条音频流在 EDL 段之间消失又出现，同步基准断一次，播放器随后就丢帧把
落下的补回来。

**修法**：`setMuted` 改成连 `aid=no` 一起设。画面轨只解码视频，段与段的
轨道布局也就一致了——**它本来就不该碰音频**，声音全归口播轨与配乐轨。

## 三、修完的效果

同一条片子播到 **01:14.29**，跨过 S6 四十多秒：

| | 修之前 | 修之后 |
|---|---|---|
| 走时异常 | 11 条，1.67× 连跑 6.5 秒 | **0 条** |
| 口播纠偏 | 10 条 | 1 条（7 秒处 −176ms，刚过阈值的正常抖动） |

## 四、判错的路

写下来是因为它们看着都很合理：

- **「是变速倍率算错了」** ——不是。切片实测 86 帧 / 2.866667 秒，
  与坑位 2.867 秒差 0.33ms。倍率一直是对的。
- **「是编码规格不一致导致解码器重建」** ——只对了一半（根因 3 是真的），
  但它造成的是**约 100ms 的停顿**，不是 6.5 秒的 1.67 倍狂奔。修完症状仍在。
- **「口播轨落后 400ms 是音频输出延迟造成的测量口径差」** ——不是。
  如果是口径差，从第 0 秒就该有；实测前 25 秒一条纠偏都没有。
- **「mpv 的 EDL 段边界 seek 不精确，画面提前了一截」** ——没有证据支持，
  也无法解释"只影响后面两三秒然后恢复"这个形状。

**共同点**：全都是坐在代码前面想出来的。真正定位靠的是两样东西——
把 EDL 打出来看，和量播放器每一拍走了多少。

## 五、留下的两样工具

它们不是临时插桩，是常驻的，因为这类问题还会再来：

**① EDL 换源日志**（`MultitrackPlayback.setPlan`）

```
画面轨换源，共 4 段：edl://%105%…,start=0.000,length=16.300;…
```

「谁在什么时候播哪个文件的哪一段」是这个产品的核心，出问题时没有它只能靠猜。
这次就是靠它证明了画面轨没有被连带加速。

**② 走时探针**（`MultitrackPlayback._checkPace`）

每 400ms 一个窗口，比对"走掉的内容时长"与"真实过去的时间"，偏离
±25% 就告警。主时钟自己不会变速，所以任何偏离都意味着播放器在停顿或追赶。

这种事只在完整播放里才撞得到，靠肉眼盯着复现不了，**必须留下量得出来的痕迹**。

## 六、这件事和代理文件的关系

根因 3 和根因 4 本质是同一件事：**EDL 各段的规格/轨道布局不一致**。

我们现在是靠「把每一条素材、每一段切片都转成原片的规格」来对付它的。
[代理文件方案](./2026-08-10-硬件兼容：用代理文件绕开，而不是逐项做兼容.md)
改成「所有东西都转成同一个固定规格」，这类问题从根上就不存在了——
`MaterialNormalizer` 那套探测与对齐逻辑也可以退休。
