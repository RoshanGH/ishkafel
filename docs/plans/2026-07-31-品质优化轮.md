# 品质优化轮（2026-07-31）

> 目标：把 app 在 UI/UX、功能设计、性能、产品体验各方面推到「高标准 to C 商业化软件」的水准。
> 方法：三路并行审计（功能完整性 / 性能 / 健壮性与工程质量）→ 按「用户影响 × 修复成本」排序 → 分文件域并行实施（各自独立 worktree，避免抢 git 索引）→ 每项 TDD + 真机验收。

## 一、审计抓到的、直接威胁产品目标的问题

产品目标是「打包发同事双击使用」的成片翻新工具。以下三条如果不修，这个目标不成立：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `ffmpeg`/`ffprobe` 走裸 PATH | `launchctl getenv PATH` 实测为空，双击 `.app` 启动的进程 PATH 不含 `/opt/homebrew/bin`。同事打开点「新建任务」直接拿到 `ProcessException`，**全部功能报废**。至今没暴露是因为验收一直走 `flutter run`（继承终端 PATH） |
| 2 | 分析中途退出 / 凭据缺失 → 任务永久卡「分析中」 | 重试入口只在 `analysisError != null` 时出现，这条路径永远够不到；全 app 无删除入口，唯一出路是去 Finder 手删 JSON |
| 3 | 任务 JSON 一个字段不合预期 → 整条从列表静默消失 | 用户看到的是「我的任务不见了」，甚至是空态引导文案 |

均已修复：ffmpeg 定位器 + 启动预检常驻横幅；僵死任务恢复 + 任务卡右键菜单（删除/重命名/重新分析）+ 子进程超时；解析容错对齐 + 跳过文件数上报 UI。

## 二、对照设计定稿补齐的 UI/UX

- **视觉镜头轨从「几根线」变成块体**：改造前只画了分隔线与选中描边，块体本身零填充，真机上几乎不可见——而「台词语义单元 ⊃ 视觉镜头」两层切分是产品核心，镜头层看不见就等于没法编辑。现在每个镜头是独立块体，填充沿用所属单元的颜色（让严格嵌套关系一眼可见），带 S 编号，选中态紫色高亮。
- **四条轨道标题兼做操作说明**：「台词语义单元（拖大边界调整）」「视觉镜头（拖小边界调整，限制在所属单元内）」。核心约束写在轨道上比藏进帮助文档有效。
- **单元块两行信息层级**：首行编号 + 时长（打标接通后换成标签名），次行台词摘要。改造前挤成一行，编号被长台词淹没。
- **左栏列表头与镜头数徽标**：「台词语义单元 · N 个」+ 每行镜头数（判断该单元要不要展开细调的关键信息）。
- **设计 token**：新增 `AppSpacing`（4pt 网格）、`AppRadius`、`AppStroke`、`AppFontSize`（5 级阶梯）。改造前散落 91 处内联数字、8 种字号（相邻两级只差 0.5px，读不出层级只会让排版发糊）。配套两条守卫测试：间距必须是 4 的倍数、已迁移目录不得出现内联 `fontSize`。
- **文案统一到术语表**：「单元详情/镜头详情」→「台词语义单元/视觉镜头」；拆分按钮区分两层；确认失败提示去技术黑话。
- **清理死按钮**：「重新 AI 切分」永久禁用且无解释 → 补禁用原因说明。

## 三、性能

| 改动 | 实测收益 |
|---|---|
| 播放位置改 `ValueNotifier` + `RepaintBoundary` | 播放时每 tick 从「重建整页 10~12ms」降到只重绘时间线一层。此前 `positionMsStream` 每秒推 30 次却走页面级 `setState`，把左栏/播放器/检查器/底部栏全拖下水，占满 60fps 预算七成 |
| 抽帧 4 路并发 + 波形不再排队等抽帧 | 进页面后两条辅助轨的空白时间从 2.2s 降到 ~1s |
| 波形按可视像素重采样 + 包络密度随片长 | 此前固定 240 桶，5 分钟素材放大 20 倍后满屏只有十几根**等高宽柱**，而用户正是靠波形找语句停顿 |
| 文字排版 LRU 缓存 | 每帧几十段文字不再重新 layout（单段约 35µs） |
| `bytesToPcm16` 去掉 `.toList()` | 省 12~38MB，包络计算提速 1.3~3.8× |
| `wrapPcmAsWav` 预分配替代展开操作符 | 主线程阻塞 75.8ms → <5ms，省 77MB 瞬时分配 |
| 任务列表局部更新 + 解码上 isolate | 100 条任务在滚动中的完成耗时 573ms → 112ms；保存后不再整页闪 spinner |

## 四、专业工具的操作补全

- **JKL 走带**（CLAUDE.md 明确要求但一直没做）、⇧±10 帧粗调、Home/End 跳片头片尾
- **↑↓ 在相邻单元/镜头间移动选中**，并同步播放头（只改选中不动画面，用户会以为没生效）
- **时间线跟随播放头**：放大后播放，播放头跑出视口时自动带回。此前放大功能等于废掉一半
- **滚轮/触控板**：⌘+滚轮以指针为锚点缩放、滚动平移、触控板双指捏合缩放

## 五、本轮踩到并记录的坑

1. **触控板手势不能分两处处理**。第一版只在 PanZoom 回调里处理 scale、把 pan 留给既有拖拽路径，结果两条路径**各自基于同一份未更新的 geometry** 回调 `onGeometryChanged`，后到的把先到的整个覆盖——捏合缩放看起来完全没生效。修法：把触控板从 `GestureDetector.supportedDevices` 去掉，平移与缩放在一处算完。
2. **抽帧缓存文件名必须带总张数**。把张数从固定 14 改成随片长后，旧的 `_tl_0..13` 会被当作新布局的前 14 张复用，而它们的时间点是按 14 张算的——胶片条与时间轴对不上，且因命中缓存不会重抽，错位会一直留着。
3. **移除页面级 `setState` 后，凡是依赖编辑器状态的子部件都要自己监听**。时间线工具条的禁用态一度会永久停在初始值（已补回归测试，回退验证过它能变红）。
4. **像素级断言要选对度量**。判断波形「密集细柱 vs 少数宽柱」时，「有墨的列数」两者都能铺满视口，必须数「相邻列柱高变化次数」。
5. **不要在验证完成前提交**。有一次全量测试尚未跑完就提交，那条捏合用例当时是红的，靠下一条提交修正并说明。

## 六点五、全量评审与闭环（当日第二轮）

对当日 46 个提交做了一次全量评审，抓到 3 个 Critical、8 个 Important、13 条
Minor、11 条测试质量问题，已全部处理。几条值得记住的：

### 自己引入又自己毁掉的那条（Critical）

抽帧「按下标回填」的槽位设计是为了防止空洞被压缩，而最后一行
`slots.whereType<String>()` 把空洞压掉了——剩余各张被按新长度重新等分铺开，
从失败点起每格显示的都是下一格的画面，尾部累计错位数秒，且 `mediaStatus`
仍是 `ready`、界面零提示。

**更值得记的是它的测试也是假绿**：守这条性质的用例因为后来改了缓存文件名
（`_tl_` → `_tl32_`）而正则匹配不上，14 张全部抛异常被 catch 吞掉、断言循环
执行 0 次，测试一直通过。另有一条既有用例把缺陷本身写成了预期（「跳过失败项」）。

### 评审自己也会错，实施者纠正了它

评审判断「`valueOrNull` 变 null 导致任务网格清空」。实际上 Riverpod 的
`AsyncNotifier.state` setter 走 `asyncTransition`，会自动 `copyWithPrevious`，
`valueOrNull` 并不会变 null——真正丢数据的是页面里 `when` 的 error 分支优先于
`hasValue`。实施者改的是页面而非照着评审改 controller，并用**变异验证**
（故意放宽实现，看断言是否立刻变红）证明新测试真的有效。

### 四条名不副实的测试

- `find.ancestor(matching: RepaintBoundary)` **恒真**：Flutter 自己在每个路由页
  外面就套了一层，路由内任何 widget 都必然有 RepaintBoundary 祖先，把实现里那行
  删掉断言照样绿。改为验渲染层的直接父节点。
- 「禁用时必须说明原因」只断言 tooltip 存在，没验按钮禁用、没验 tooltip 说了什么。
- 「纵向滚动也用于平移」只断言「回调触发了」+「不是缩放」，没验平移方向与幅度。
- token 守卫只覆盖一个目录、正则只匹配 `fontSize:` 漏掉 `fontSize =`、间距完全没守。

### 另一条自引入的隐患

给四条轨各加 14px 标题条后，时间线总高 192 → 248px，而 xib 默认的 800×600 窗口下
时间线区只有约 145px——**音频波形轨整条落在可视区外**，为它加的「生成中/失败」
占位用户根本看不到。现已按时间线反推窗口最小尺寸（1100×880）并加纵向滚动兜底，
把「轨道总高」与「最小窗口尺寸」的关系钉进测试。

## 七、阶段②（M4）的前期地基与一条待产品确认的事

已先于 UI 落地两块纯后端能力（`lib/core/miaoa/`）：

- `MiaoaContentService`：三种互斥检索模式 → miaoa CLI 的三组参数
  （`--public-tag` + and/or ｜ `--keyword X --by content` ｜ `--like-image <fileKey>`），
  全部限定 `--type storyboard`（替换的是视觉镜头，对应分镜库；成片库是整条片子）
- `CandidateProbe` + `judgeDurationFit`：候选规格探测与 ±15% 时长匹配判定

### ⚠️ 待产品确认：miaoa 不返回候选素材的时长与分辨率

真机实测（`miaoa content search` 与 `miaoa content get` 各取样）：分镜库记录的
`mediaFile.duration` 与 `mediaFile.resolution` **全部为 null**（20/20）。

这直接影响两条已定决策：
- 「时长对齐 ±15% 容忍度」——候选卡的时长差徽标（绿=容忍内 / 橙=超限）算不出来
- 「分辨率适配」——低清候选（低于输出 1/1.5）的「低清」徽标算不出来

**当前兜底**：用 ffprobe 直接读候选的签名预览 URL 探测。实测可行
（1920×1080 / 59.94fps / 6.138s，单条约 3 秒，只读文件头不下载整片），
结果按素材 id 缓存，失败时候选卡退化为不显示时长差而不是阻断选材。

**需要决策**：是接受这个兜底（候选面板要做「探测中」的渐进填充与并发控制），
还是推动 miaoa 后端在分镜记录上补齐这两个字段。后者更彻底，但跨团队。

附注：抽样到的候选素材是 **59.94fps**——正是本轮修掉的 `frameMs` 误判帧率区间，
真接进来就会踩上。
