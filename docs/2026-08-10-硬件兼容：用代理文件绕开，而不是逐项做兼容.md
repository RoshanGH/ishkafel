# 2026-08-10 硬件兼容：用代理文件绕开，而不是逐项做兼容

> 结论先写在前面：**不要为 Intel 做一套降级分支。改成代理文件，兼容问题
> 自己就没了**，而且顺带解决了替换点顿挫和老机器预览卡顿。
>
> 状态：已决策，未实施。实施前需先确认 miaoa CLI 的 x86_64 版本（见文末）。

---

## 一、问题从哪来

同一个人在两台机器上做**一模一样**的事：

| | 机器 | 场景 |
|---|---|---|
| 家里 | Apple Silicon | 主力 |
| 公司 | Intel Mac | 主力 |

于是「app 能不能在 Intel 上跑」不是一个可选项。

### 现在的架构为什么在 Intel 上会挂

问题不在 Flutter，也不在播放器——media_kit 的预编译库是
`macos-arm64_x86_64`，两个架构都覆盖，当前产物是 arm64 thin 只是 Debug 的
`ONLY_ACTIVE_ARCH = YES` 所致，改构建配置即可。

**真正会挂的是我们自己定的一条规矩：「所有素材向原片规格看齐」。**

素材规格化（`MaterialNormalizer`）与变速切片（`SpeedFitter` →
`ExportCommands.fitCandidateVideo`）都会读原片规格，然后照着编：

```
原片：hevc / Main 10 / yuv420p10le / 1080x1920 / 30fps
     ↓ 照抄
素材、切片：hevc_videotoolbox -profile:v main10 -pix_fmt p010le
```

这在 Apple Silicon 上没问题（实测 11 秒素材 2.4 秒转完）。但
**Intel Mac 的 VideoToolbox 绝大多数只支持 8bit HEVC 编码**，
`-profile:v main10` 直接失败——素材规格化和变速切片两条路同时断掉。

也就是说：**原片是什么规格，全链路就被绑死在什么规格上**。原片来自客户、
来自剪映导出、来自各种手机，规格不受我们控制，却决定了本机能不能干活。
这条规矩本身就是错的。

---

## 二、行业怎么做的：代理剪辑

剪映专业版、Final Cut Pro、Premiere、DaVinci 都有同一个东西——**代理**
（proxy / 代理模式 / 优化媒体）：

> 导入时另生成一份**统一规格的低码率副本**，剪辑与预览全程用副本，
> **导出时才回到原始素材**。

它解决的从来不是"画质"，而是三件工程上的事：

1. **把千奇百怪的输入收敛成一种规格**。用户素材可能是 HEVC 10bit、ProRes、
   VP9、各种帧率，编辑器不可能为每一种做适配——转成一种就只剩一种。
2. **让预览的性能与原片解码难度脱钩**。4K HEVC 拖不动，720p H.264 谁都能放。
3. **让拼接不需要转码**。所有片段规格一致，时间线上任意剪接、替换都不用重编。

剪映把它做成一个性能选项（画面卡顿时开启），专业软件里则是导入时的常规
步骤。差别只是默认值，机制是同一个。

**这套做法和我们的处境是严丝合缝的**：我们的时间线本质上就是"原片若干段 +
候选素材若干段"的拼接，而拼接段规格不一致正是这两天所有播放问题的根源
（见 [替换镜头为什么会加速播放](./2026-08-10-预览接缝：变速镜头为什么会加速播放.md)）。

## 三、我们要怎么改

### 代理规格

一个**常量**，不再从原片探测：

```
H.264 High / yuv420p / 8bit / 720x1280 / 与原片同帧率
```

选它的理由：2010 年后的 Mac 全都能硬编硬解，软编（libx264）也快；
9:16 竖屏降到 720 宽，预览看清画面绰绰有余。

### 谁要转成代理

- 原片（导入时，与现有分析流程并行）
- 每一条落地的候选素材（下载后，即现在 `MaterialNormalizer` 的位置）
- 变速切片（本来就是现生成的，直接编成代理规格）

于是**预览链路上的每一段都是同一个规格**，EDL 拼起来天然一致。

### 边界（必须锁死）

> **导出只能用原始素材，绝不能用代理。**

代理是 720p 低码率，拿它导出等于把成片画质砍掉。这一条要在代码里挡住，
不能靠人记得——导出路径必须从任务的 `sourcePath` 与
`material_cache/` 的原始下载取，永远不碰代理目录。

## 四、这一步能解决什么

一箭四雕，每一项都是当下真实存在的问题：

| 解决的问题 | 现在的样子 | 代理之后 |
|---|---|---|
| **Intel 编不了 Main 10** | 素材规格化与变速切片直接失败 | 不碰 10bit，无需探测、无需降级、无需向用户解释 |
| **替换点顿挫 / 加速** | 靠 `MaterialNormalizer` 逐条把素材转成原片规格来对付 | 规格天然一致，那套对付逻辑可以退休 |
| **老机器预览卡** | 1080×1920 HEVC Main 10 软解吃力 | 720×1280 H.264，解码压力小一个量级 |
| **磁盘占用** | `material_normalized/` 存的是原片规格（高码率） | 代理码率低，比现在更省 |

**它是简化，不是加复杂度**：`MediaSpec` 那套「探测原片规格 → 逐项对齐」的
逻辑大半可以退休，目标规格退化成一个常量。

### 代价

导入时多一步转码。96 秒 1080×1920 HEVC → 720×1280 H.264：
Apple Silicon 约 10~20 秒，Intel 约 30~60 秒。一次性，且可与现有分析流程
（抽音频 / 分离 / 转写 / 打标）并行，实际不额外让人等。

产物纳入 `TaskArtifacts` 统一管理，任务删了跟着删。

## 五、哪些该上云，哪些不该

按同一条线判断：**实时交互的留本地；算得慢、吃硬件、但用户等得起的上云。**

### 真正该上云的只有一个：人声分离

| 判据 | 现状 |
|---|---|
| 装不装得动 | 本地要 1GB 的 Python/PyTorch 环境 + 700MB 模型，**唯一一个没法打包进 app 的依赖** |
| 吃不吃硬件 | M1 Pro 走 Metal 15 秒；Intel 没有 Metal，同样的活要几分钟 |
| 用户等不等得起 | 发生在分析阶段，本来就在看进度条，多十几秒无感 |

三条全中。上云之后 `audio-separator` 这个依赖整个消失，两台机器都不用装。

**未决**：需要先确认云端有无对应能力，没有则要自建一个服务。这是本文里
唯一有真实成本的一项，值得单独评估。

### 其余各就各位

| 环节 | 在哪 | 理由 |
|---|---|---|
| ASR 转写 / 语义切分 / 打标 / TTS 配音 | 已在云端 | 不动 |
| 预览播放 | 本地 | 实时交互，上云不可能 |
| 镜头切点检测 | 本地 ffmpeg + 云端画面复核 | 不动。Intel 上只是慢一点 |
| 缩略图 / 波形 | 本地 ffmpeg | 快，没必要 |
| **导出合成** | **本地** | 软编 libx264 所有机器都能跑，Intel 只是慢；上云要传原片，得不偿失 |
| 素材规格化 / 变速切片 | 本地 | **改代理规格**，见上 |

## 六、还没解决的：miaoa CLI 的架构

**这是唯一可能推翻整个计划的前提。**

```
$ file ~/.local/bin/miaoa
Mach-O 64-bit executable arm64          ← 没有 x86_64 slice
```

Rosetta 只能让 Apple Silicon 跑 x86_64，**反过来不行**——Intel Mac 上这个
CLI 根本起不来。而它不只管登录：**标签组词表也从它读**。

所以公司那台 Intel 上如果没有 x86_64 版 CLI，能做的只剩导入、语义切分、
播放、导出原片——**挑替换素材和打标全没了，也就是这个产品的核心价值全没了**。

**下一步动作**：在 Intel 机器上跑一次 miaoa 的 `install.sh`。安装脚本通常按
平台下发不同二进制，很可能自然就装上 x86_64 版；若报 unsupported platform，
则需要向 miaoa 团队要 Intel 或 universal 版本。

（按既定约定：install.sh 报 unsupported platform 就停下，不要自行寻找替代
安装途径。）

## 七、顺带

- **universal 构建**：Release 出 arm64 + x86_64，顺手做，不单独算一件。
- **代码签名**：没有 Apple Developer 账号，ad-hoc 签名即可——两台都是自己的
  机器，去一次隔离属性就行。真要发给别人时再补 Developer ID + 公证，构建
  脚本按公证流程预留。
- **AI 凭据**：两台都是自己的机器时 `--dart-define` 编进去没有泄露风险。
  但设置页仍值得做（换 key 不必重新构建），排在上面两件之后。
  ⚠️ 一旦要把包给别人，编进去的 key 就跟着包走，`strings` 可扒。

---

## 执行顺序

1. **确认 Intel 上 miaoa CLI 可用**（一分钟，决定后面所有事）
2. **代理文件**（同时解决兼容、顿挫、卡顿三件事；不依赖第 1 步，可先做）
3. **人声分离上云**（消灭最后一个装不动的依赖）
